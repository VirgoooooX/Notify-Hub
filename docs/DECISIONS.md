# 架构决策记录

本文记录当前阶段已经确定的关键决策。后续若要改变，应新增决策条目并说明迁移方案，不应静默修改原有边界。

---

## ADR-001：采用模块化单体

**状态：已接受**

### 决策

Notify Hub 初期使用单仓库、单后端、单前端、单数据库、单 Docker 镜像。

### 原因

- 个人/家庭使用规模不需要微服务；
- 部署和备份简单；
- 插件、通知、提醒需要共享一致事务和管理界面；
- 通过模块接口仍可保持清晰边界；
- 后续可拆 API、Worker 和 Plugin Worker。

### 后果

第一阶段只能运行一个 SQLite 实例；插件异常隔离必须由 Plugin Runtime 完成。

---

## ADR-002：核心平台与监控插件同仓同部署

**状态：已接受**

### 决策

不再单独维护 `monitor-pack`。监控能力以插件形式位于 Notify Hub 仓库并由平台调度。

### 原因

- 一个管理后台；
- 一个部署单元；
- 统一配置、Secret、状态和日志；
- 更适合持续增加小型监控需求。

### 约束

同仓不代表直接耦合。插件必须通过 PluginContext 和 EventService 与核心交互。

---

## ADR-003：插件只发现事件，不直接发送通知

**状态：已接受**

### 决策

插件调用 `context.emit_event()`；企业微信发送、接收人解析、去重和重试由核心完成。

### 原因

- 避免每个插件重复实现渠道；
- 统一权限和审计；
- 渠道变化不影响插件；
- 防止 Secret 扩散；
- 保证可靠队列和投递记录。

---

## ADR-004：事件、通知、投递三层模型

**状态：已接受**

### 决策

- Event：发生了什么；
- Notification：准备发送什么；
- Delivery：发给谁以及当前状态。

### 原因

一个事件可能产生多个消息和多个接收人；每个接收人的发送结果应独立记录。

---

## ADR-005：事件先落库，异步投递

**状态：已接受**

### 决策

Event API 在 Event、Notification 和 Delivery 成功持久化后返回 `202 Accepted`。不在请求线程中依赖企业微信发送成功。

### 原因

- 企业微信临时故障不影响事件接收；
- 进程重启后可恢复；
- 可实现统一重试和历史；
- 调用方获得明确“平台已接管”的语义。

---

## ADR-006：初期使用 SQLite

**状态：已接受**

### 决策

MVP 使用 SQLite + WAL，限制单实例。

### 原因

- 自托管部署简单；
- 无额外数据库容器；
- 当前预期负载低；
- 备份恢复容易。

### 迁移条件

多实例、高写入竞争、高可用或复杂报表时迁移 PostgreSQL。

---

## ADR-007：独立企业微信“系统通知”应用

**状态：已接受**

### 决策

Notify Hub 使用独立企业微信应用，不复用 family-finance 或 MoviePilot 应用。

### 原因

- 来源清晰；
- 权限和 Secret 隔离；
- 任一业务系统升级不影响通用通知；
- 可独立配置可见范围和菜单。

## ADR-008：family-finance 和 MoviePilot 不做改造

**状态：已接受**

### 决策

两套系统继续负责各自业务和自身通知。Notify Hub 只承载新建的通用监控和提醒。

### 后续

若未来希望统一部分通知，可由它们调用 Notify Hub Event API，但不是 MVP 依赖。

---

## ADR-009：第一阶段只运行可信插件

**状态：已接受**

### 决策

插件来自仓库内置或管理员手工部署的审核代码，可在宿主进程中受控运行。暂不提供在线上传和任意安装。

### 原因

Python 进程内无法真正隔离恶意代码。先建立稳定插件契约，再在后续引入子进程/容器沙箱。

---

## ADR-010：插件调度和状态持久化

**状态：已接受**

### 决策

插件调度配置、运行历史和采集游标进入数据库。进程内调度对象不是事实来源。

调度同时持久化“是否跟随 Manifest 默认值”的来源状态。普通插件配置与调度使用独立写入语义：
未提交调度时必须保留当前值；管理员自定义 interval/cron 后不再跟随插件升级，显式恢复默认后才重新跟随。

### 原因

服务重启后必须恢复；后台需要查询；插件 emit 失败时不能丢失游标语义。

---

## ADR-011：幂等键由来源提供，数据库唯一约束兜底

**状态：已接受**

### 决策

唯一键为：

```text
(source_type, source_id, event_key)
```

Codex 插件使用帖子 ID，而不是内容哈希或当前时间。

### 原因

内容可能编辑、截断或跨来源格式不同；来源原生 ID 通常最稳定。

---

## ADR-012：提醒属于核心，不属于插件

**状态：已接受**

### 决策

单次提醒、周期提醒、持续催办、确认和延后由 ReminderService 负责。

### 原因

提醒需要统一的生命周期、收件人确认、时区和恢复机制，不应由每个插件重复实现。

---

## ADR-013：自然语言只产生草稿，确认后写正式提醒

**状态：已接受**

### 决策

规则解析器或 LLM 返回结构化 ReminderDraft；业务层校验并向用户展示，用户确认后才创建 Reminder。

### 原因

避免日期歧义、模型幻觉或错误接收人导致误提醒。

## ADR-014：先文本和图文，后语音

**状态：已接受**

### 决策

`v0.1.0` 实现文本和图文出站。语音输入、ASR、TTS 和 voice 消息放到后续版本。

### 原因

首版核心风险是可靠投递和插件系统，语音会引入媒体下载、转码、临时文件和模型依赖。

## ADR-015：推荐 FastAPI + Vue 3

**状态：已接受**

### 决策

- 后端：Python/FastAPI/Pydantic/SQLAlchemy/Alembic；
- 前端：Vue 3/TypeScript/Vite。

### 原因

- Python 适合监控插件和已有脚本迁移；
- FastAPI 便于异步 API、OpenAPI 和 Pydantic 契约；
- Vue 适合快速构建自托管后台；
- 与用户已有项目技术经验接近。

具体依赖版本在工程初始化 PR 中锁定，不在本决策文档写死。

## ADR-016：API Client 与管理员身份分离

**状态：已接受**

### 决策

外部事件使用独立 API Key，管理员后台使用独立认证。API Key 不能登录后台。

### 原因

权限、轮换、审计和限流语义不同，混用会扩大泄露影响。

## ADR-017：不提前引入 Redis 和消息中间件

**状态：已接受**

### 决策

MVP 使用数据库队列和持久化调度。只有出现明确瓶颈或多实例需求时再引入额外基础设施。

### 原因

减少部署复杂度和故障点；当前负载无需 Redis/RabbitMQ。

## ADR-018：首个插件为 Codex X Monitor

**状态：已接受**

### 决策

使用最初的 X/Twitter 监控需求验证插件、状态、事件、去重、调度、企业微信投递和后台管理完整闭环。

### 完成标准

同一帖子不重复、首次 baseline 不误发、平台失败不推进游标、重启后状态恢复。

## ADR-019：v0.3.0 使用可插拔本地媒体能力

**状态：已接受**

### 决策

ASR、TTS 和音频转码通过 Adapter 接入。基础镜像不内置模型权重；本地实现以无 shell 的受限 argv 命令运行，并通过挂载提供模型或可执行程序。

### 原因

- 保持文本事件核心可部署、可降级；
- 避免把未选定版本和许可的大模型固化进镜像；
- 允许按设备能力选择 SenseVoice 或其他本地实现；
- 统一超时、输出限制、临时文件和错误归一化。

## ADR-020：持续提醒确认状态与事件幂等语义

**状态：已接受**

### 决策

- `awaiting_ack` 为派生展示状态，不扩展 Reminder 持久化枚举；
- `any` 任一确认即完成，`all/each` 在全部接收人终止后完成且已确认成员不再接收；
- Event 首次与重复提交均返回 `202`，重复返回原 ID；
- Reminder 触发始终先产生 Event，再路由为 Notification/Delivery。

### 原因

保持已有状态机和“平台已接管”HTTP 语义稳定，同时消除专题文档与核心领域模型之间的歧义。

---

## ADR-021：废除 Secret 与普通配置的物理隔离机制

**状态：已接受**

### 决策

废除先前必须将敏感 Secret（如主密钥、JWT 密钥、企业微信 Token/AES key 等）通过 Docker Secret 物理挂载文件独立部署的规定。允许并在 Docker Compose 中推荐使用直接通过环境变量传递 Secret 的方式（以 Shell 或同级目录 `.env` 文件插值代入），从而废除 `/run/secrets` 下的密文小文件读取逻辑。

### 原因

- 简化单机和家庭环境自托管的部署与配置工作，不再需要额外创建多个零散的物理 Secret 文件。
- Pydantic Settings 和 `entrypoint.sh` 已能直接支持从纯环境变量中高效读取对应的敏感参数。
- 只要限制 `.env` 及宿主环境本身的读取权限，对该定位的低风险单机部署应用而言，安全性是完全足够且可接受的。

### 后果

- 部署目录中不再推荐创建 `secrets/` 文件夹。
- entrypoint.sh 移除了专门的 `_FILE` 转环境变量转换逻辑。
- 环境变量必须小心保管，不得提交明文到公共版本库。

## ADR-022：AI 作为核心 Gateway 能力

**状态：已接受**

### 决策

Provider、API Key、模型 Profile、缓存、预算、结构化校验和调用日志属于核心平台。Profile 是可复用运行策略，定义单一能力类型、模型路由、生成/输出策略和成本可靠性约束；具体业务 Prompt、标签和字段留在插件。插件只能调用 Manifest 明确授权且能力匹配的 `context.ai` Profile，并提供业务 instruction 与待分析数据；插件不得保存或指定 Provider URL、Key、任意请求头或模型。

第一版使用 OpenAI-compatible Chat Completions 作为最低公共协议，并保留后续 Responses 协议扩展点。防提示注入、禁用工具和结构化 Schema 校验是 Gateway 强制规则，不作为 Profile 开关。Provider 和 Profile 使用软删除保留调用审计；Provider 被未删除 Profile 引用时禁止删除，Profile 被启用插件引用时禁止删除。AI 返回结构化建议，Event 去重、是否发送和 checkpoint 仍由确定性代码负责。

### 原因

- 更换 Provider 或模型不需要逐个修改插件；
- 密钥、SSRF、预算、缓存和审计可集中治理；
- AI 故障不会绕过可靠事件与投递边界；
- 同一输入可跨插件运行和进程重启复用缓存，减少调用费用。

## ADR-023：提醒定义、执行实例与催办投递分离

**状态：已接受**

### 决策

- `Reminder` 保存长期定义与下一次计划时间；
- 每个计划时间生成唯一的 `ReminderOccurrence`；
- 每个实例和接收人生成 `ReminderOccurrenceRecipient`，独立保存确认、通知次数和下次催办时间；
- Planner 只创建持久化实例，Escalation Worker 使用带租约的数据库 claim 创建 Event；
- 只有 Event 返回 accepted 或 duplicate 后才推进通知次数；
- 完成和取消 Delivery 必须按 Occurrence、必要时再按接收人限定，不能影响周期提醒的其他实例。

### 原因

周期触发和同一轮持续催办是两套时间语义。分离后，完成今天的实例不会结束长期定义，Worker 崩溃或 Event 暂时失败也不会丢失提醒或消耗通知次数。

## ADR-024：交互式提醒使用普通消息与底部自定义菜单

**状态：已接受**

### 决策

- 新的企业微信交互式提醒使用普通文字、图文或图片消息，不再依赖模板卡片按钮；
- 消息末尾提示用户通过底部【快捷操作】菜单处理最近收到的交互式提醒；
- 企业微信应用底部菜单固定为“新建提醒”“我的提醒”“快捷操作”三个系列；
- 【快捷操作】提供“完成本次”“推迟10分钟”“推迟30分钟”“今日忽略”“停止本次”五个动作；
- 【新建提醒】启动文字创建会话或打开当前 UserID 的短期签名创建页，【我的提醒】打开当前 UserID 的短期签名列表页；
- 系统按企业微信 UserID 维护 `latest_interactive_occurrence_id`，始终操作该用户最近一次成功发送的交互式提醒；
- 只有交互式提醒成功投递才更新指针，普通通知、系统消息和操作确认消息不更新；新指针覆盖旧指针，目标失效后不自动回退；
- 每次操作结果必须包含任务名称，不得只返回“操作成功”；
- 已存在的模板卡片、NotificationAction 和 Action Token 只作为历史兼容路径保留。

### 原因

普通图文消息和企业微信应用底部自定义菜单在企业微信客户端及个人微信中的企业微信插件都能使用，覆盖面比依赖模板卡片按钮的交互方式更稳定。以最近成功发送的交互式提醒为目标，能够在第一版避免引入任务编号选择和额外页面。

### 范围

本决策只改变企业微信菜单入口及交互式提醒的发送与操作入口，不改变提醒创建规则、Once/Interval/Cron 调度、插件系统、普通通知流程、Reminder 整体领域模型或小程序。菜单中的创建和查询项复用既有会话与移动 Web 能力。

## ADR-025：Web 管理员广播提醒使用成员快照和分阶段投递

**状态：已接受**

### 决策

- 只有后台 Web 管理员可以创建企业微信 `@all` 广播提醒；微信菜单、移动端、插件和普通 Client Reminder API 不开放该能力；
- `@all` 只决定接收范围，与 Once/Interval/Cron 调度、消息内容类型和是否交互相互独立；普通广播只发送消息，不要求确认；
- 创建时冻结所有启用且绑定有效企业微信 UserID 的 Person；启用交互时，完成统计只以该快照为准；
- 第一条消息通过企业微信原生 `@all` 发送；仅交互式广播会继续逐人催办快照中仍未完成的成员；
- 交互式广播可由管理员选择确认策略；“全员完成后通知”是独立可选项，仅在 `all` 策略下开放；
- 开启完成通知后，只有快照成员全部真实完成才可靠排队“所有人都已完成”的 `@all` 广播，停止、取消和过期均不视为完成；
- 原生 `@all` 成功后，快照成员的每个有效 UserID 都指向该 Occurrence，菜单操作仍只改变点击者自己的接收人状态；
- 所有持续提醒在标题和正文中明确标记“持续提醒”“需要确认”和完成入口，避免用户误认为是一次性通知；
- 广播创建必须审计，并在 Web 明示企业微信应用可见范围必须与 Notify Hub 成员清单一致。

### 原因

企业微信原生 `@all` 不提供可靠的实际收件人回执，不能单独支撑逐人确认。成员快照提供可审计的完成集合；发送对象、交互行为和完成反馈分开配置，可以同时覆盖“只通知所有人”和“要求所有人完成”的不同场景。

### 后果

未登记到 Notify Hub 的企业微信成员可能收到首次广播，但不会被纳入完成统计，也不会收到后续逐人催办。管理员必须在发布前校准应用可见范围和 Notify Hub 身份清单。

## ADR-026：统一 UTC 时间点、IANA 墙钟时间与 DST 语义

**状态：已接受**

### 决策

- Event、Notification、Delivery、Reminder 执行状态、AI 调用和其他持久化时间点在领域与 ORM 边界都使用带时区的 UTC `datetime`；SQLite 返回的无时区历史值只在 ORM 读取边界解释为 UTC。
- API 的绝对时间必须使用带 offset 的 RFC 3339。Reminder 等由用户选择的本地计划时间以“本地墙钟值 + IANA 时区”表达，由后端解析，前端不得先按浏览器时区转换；兼容旧客户端时，计划字段中已带 offset 的 RFC 3339 值视为调用方已经解析好的绝对时间，DST 缺口和重复时刻策略只作用于无 offset 的墙钟值。
- 平台时区由持久化设置提供运行时默认值，修改后立即影响后续请求；已创建的 Reminder 和 Plugin Schedule 保存并继续使用自身时区，不随平台默认值漂移。
- Interval 表示经过时长；Cron 和 RRULE 表示指定 IANA 时区中的墙钟规则。DST 跳时造成的不存在时刻跳过，重复时刻固定选择第一次出现（`fold=0`）。所有下一次执行时间最终归一化为 UTC。

### 原因

- SQLAlchemy 的 `DateTime(timezone=True)` 不能让 SQLite 自动保留时区，若在业务层零散修补，嵌套响应、比较和新功能仍会继续泄漏无时区值；
- `datetime-local` 本身不携带时区，浏览器所在时区可能与计划时区不同，提前调用 `toISOString()` 会静默改变用户选择的时刻；
- Cron、RRULE 和 Plugin Schedule 若分别实现 DST 规则，会在春季缺口和秋季重复时刻产生不同执行结果；
- 平台默认时区是可修改配置，不应被硬编码或冻结为进程启动快照。

### 兼容与迁移

- ORM 底层仍使用现有数据库列类型，本决策本身不要求修改 SQLite 表结构；发布前仍需完成一致备份和 Alembic 空库升级验证。
- 现有 SQLite 无时区时间值按项目原有约定视为 UTC。若部署曾由外部程序写入本地墙钟值，升级前必须单独审计和校正，不能由应用猜测。
- 旧客户端若向绝对时间字段提交无 offset 值将收到稳定的校验错误；计划表单应改为同时提交本地墙钟值和 IANA 时区。
## ADR-027：公众号文章发布作为平台渠道能力

**状态：已接受**

### 决策

新增 `mp_article` 投递渠道。插件只通过 `EventDraft.publish_to_mp` 表达发布意图并提供文章标题、正文、封面和摘要；公众号 AppID/Secret、Access Token、永久素材、草稿与发布调用全部由核心 `channels/mp` 负责。发布事件必须同时满足：

- `message_type == "article"` 且携带封面；
- 不与 `@all` 广播组合；
- Manifest 声明 `publish_mp: true` 权限，运行时缺少权限直接拒绝。

插件是否发布仍由确定性规则和 AI 分类置信度阈值决定；AI 摘要（`summarize`）只生成文章正文，失败时回退确定性摘要，不参与发布决策。`mp_publish_mode` 支持 `draft`（仅建草稿）与 `publish`（建草稿后提交发布）。未配置公众号凭证的投递按不可重试错误进入 dead，不隐式降级为文本通知。

### 原因

- 插件保持“只发现事件”的边界，渠道凭证和微信接口调用集中在核心；
- 公众号发布复用既有 Event/Notification/Delivery 的幂等、重试和审计链路；
- AI 作为建议层，不获得“是否发布”的决定权；
- 未启用公众号的插件（fabrizio_hwg_monitor、docker_log_monitor 等）完全不受影响。

### 后果

- Delivery 新增 `recipient_type=publish` 与 `channel=mp_article`；
- 新增环境变量 `NOTIFY_HUB_MP_APP_ID`、`NOTIFY_HUB_MP_APP_SECRET`、`NOTIFY_HUB_MP_PUBLISH_MODE`、`NOTIFY_HUB_MP_AUTHOR`；
- 既有企业微信投递路径保持不变。
## ADR-028：公众号文章库与人工最终发布（library 模式）

**状态：已接受**

### 决策

在 ADR-027 的官方 API 路径之外，新增 `library` 文章库路径，两条路径并存：

- `mp_publish_mode=library` 或未配置 AppID/Secret 时，`mp_article` 投递不再进入 dead，而是把文章写入 `mp_articles` 文章库（状态 `ready`），通过管理后台「公众号文章」工作台预览、复制公众号富文本格式，或由 Tampermonkey 脚本一键填入公众号后台；**发布按钮不自动点击，最终发布由管理员人工确认**。
- 显式配置 `mp_publish_mode=draft|publish` 且凭证完整时，仍走 ADR-027 官方 API 路径（上传永久素材 → 建草稿 → 可选提交发布），文章同时记录到文章库作为历史。
- 状态机：`draft/ready → published | ignored`，`ignored/published → ready`（restore）。`published` 与 `ignored` 之间不允许直接转换。
- 文章库只存储平台生成、内容已转义的 HTML；前端预览按只读处理，禁止回填到插件或渠道。

### 原因

- 个人主体订阅号不能使用公众号官方发布 API（无认证/服务号能力），但插件已完成的 AI 判断、翻译、封面和排版不应浪费；
- 把“生成/排版/保存”与“最终发布”分离，既保留官方 API 自动化，又为个人号提供可靠的半自动路径；
- 人工最终发布比无人值守自动化更稳，且不需要维护微信模拟登录态。

### 后果

- 新增 `MpArticle` 模型与迁移 `0014_add_mp_articles`、管理 API `/api/v1/admin/articles*` 和前端文章工作台；
- `ChannelMessage` 增加 `delivery_id`，文章库按 delivery 幂等落库；
- 新增 `scripts/wechat-mp-import/notify-hub-mp-import.user.js` 浏览器导入脚本；
- ADR-027 中“未配置公众号凭证即进入 dead”的行为仅对显式 `draft|publish` 模式保留，未配置凭证默认走 `library`。
